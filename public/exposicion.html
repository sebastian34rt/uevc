INSTITUCIÓN EDUCATIVA • DEFENSA DE PROYECTO TECNOLÓGICO

SISTEMA WEB INTEGRAL REMIX REMIX INSTITUTO

Portal Institucional, Plataforma de Sorteos Unívocos en Tiempo Real y Centro de Operaciones de Ciberseguridad (SOC)

Documento maestro, guion para expositor minuto a minuto, arquitectura de software, fundamentos teóricos y banco de preguntas de sustentación ante jurado evaluador.

Área / Carrera: Ingeniería de Sistemas / Desarrollo de Software Web
Plataforma: React 18 + Vite + TypeScript + Tailwind CSS + Firebase Cloud Suite
Modalidad: Progressive Web App (PWA) + Arquitectura Serverless Reactiva
Despliegue: Producción Web Hosting (cPanel Apache/LiteSpeed) + Firebase Realtime DB
Versión: 3.5.0 Enterprise Release

1. Introducción y Planteamiento del Problema

En la actualidad, las instituciones educativas enfrentan desafíos multidimensionales que van más allá de la mera docencia académica. Entre ellos destacan la necesidad de una comunicación digital transparente, la captación de nuevos estudiantes mediante procesos de admisión ágiles, y de forma crítica, la sostenibilidad financiera y recaudación de fondos mediante actividades extracurriculares como rifas y sorteos benéficos institucionales.

Históricamente, los sorteos escolares o benéficos se han gestionado mediante talonarios de papel físicos o sistemas improvisados de hojas de cálculo. Este enfoque acarrea fallas sistemáticas críticas:

  • Falta de trazabilidad y fraude: Talonarios duplicados, boletos perdidos y quejas de participantes que dudan de la transparencia del sorteo.
  • Vulnerabilidad de datos personales: Exposición de listas con nombres, teléfonos y correos al alcance de cualquier persona.
  • Fragmentación tecnológica: La institución suele tener una web informativa por un lado, un sistema de boletos por otro, y nula protección contra ciberataques.
Propuesta de Valor de este Proyecto: Se diseñó e implementó un ecosistema unificado que integra en una sola plataforma la identidad institucional, un sistema de sorteos con verificación criptográfica pública y registro unívoco, un módulo de inventario por códigos QR, y un Centro de Operaciones de Ciberseguridad (SOC) con capacidad de bloqueo reactivo en tiempo real.

2. Objetivos del Proyecto

2.1. Objetivo General

Desarrollar y desplegar una plataforma web integral, modular y de alto rendimiento que centralice la gestión académica, la interacción con la comunidad estudiantil y el control automatizado y transparente de eventos de sorteos benéficos, respaldado por estándares modernos de ciberseguridad y compatibilidad multiplataforma PWA.

2.2. Objetivos Específicos

  1. Desarrollar un Portal Institucional Dinámico: Proveer módulos de oferta académica, noticias, admisiones, testimonios, galería y mesa de ayuda con tutoría interactiva.
  2. Implementar un Módulo Criptográfico y Unívoco de Sorteos:
    • Permitir la generación masiva de boletos con códigos alfanuméricos únicos y código QR de validación.
    • Habilitar la consulta pública donde el usuario ingresa su código y registra su boleto con sus datos (nombre, teléfono y correo).
    • Blindaje de registro: Una vez registrado, el boleto queda perpetuamente sellado mostrando únicamente "Registrado por: [Nombre]", eliminando para el público la opción de borrarlo, editarlo o alterar datos ajenos.
    • Garantizar una ruleta visual de selección aleatoria en vivo libre de sesgos para la transmisión del sorteo.
    • Crear una función de "Bloqueo de Emergencia / Modo Sorteo" en el panel de control, que permite congelar temporalmente la web institucional y enfocar todo el tráfico en el evento de sorteo activo.
  3. Asegurar la Solución con Módulos de Ciberseguridad (SOC): Monitor de ataques, filtrado de direcciones IP maliciosas, registro de eventos de auditoría y autenticación de administradores con roles RBAC.
  4. Garantizar Disponibilidad Multiplataforma (PWA): Capacidad de instalación en dispositivos móviles y de escritorio sin pasar por tiendas de aplicaciones, con caché offline.

3. Marco Teórico y Arquitectura Tecnológica

Para garantizar escalabilidad, tiempos de carga inferiores a 1 segundo y máxima seguridad, la solución fue concebida bajo el paradigma JAMstack moderno con desacoplamiento entre capa de presentación y persistencia en la nube.

Capa / Componente Tecnología Seleccionada Justificación de Ingeniería
Frontend Core React 18 + TypeScript Virtual DOM para re-renderizado reactivo; TypeScript aporta tipado estático eliminando errores en tiempo de compilación.
Empaquetador Vite Bundler (ESBuild + Rollup) Compilación ultra-rápida basada en módulos ES nativos y generación de chunks minificados para distribución estática.
Estilos y UI Tailwind CSS Diseño atómico sin sobrecarga de clases huérfanas, responsive mobile-first y optimización vía PurgeCSS.
Base de Datos y Nube Google Firebase Firestore Base de datos NoSQL documental distribuida a nivel mundial, con listeners en tiempo real (`onSnapshot`) y reglas de seguridad granulares.
Autenticación Firebase Authentication Tokens JWT seguros, gestión de sesiones cifradas y control estricto de roles administrativos.
Offline y PWA Workbox Service Workers Estrategia de caché `Stale-While-Revalidate` que permite a los usuarios navegar incluso con conexiones inestables.
Servidor Web Hosting Apache / LiteSpeed (cPanel) + .htaccess Reglas de reescritura mod_rewrite para Single Page Application, compresión GZIP/Brotli, forzado HTTPS 301 y headers de seguridad HTTP.
Fundamento de Ciberseguridad y Manejo de Datos: A diferencia de las aplicaciones web convencionales donde las consultas de base de datos viajan sin cifrar, en esta plataforma la comunicación se realiza mediante canales seguros HTTPS / TLS 1.3 con validación de tokens en cada petición hacia Firebase. Las credenciales nunca se exponen al cliente y el acceso administrativo está protegido por guardas de ruta (Route Guards) y verificación de roles.

4. Módulos y Funcionalidades del Sistema

4.1. Módulo 1: Portal Institucional & Admisiones

Diseñado para proyectar la identidad académica de Remix Remix Instituto. Incluye catálogo de carreras, panel de testimonios de egresados, noticias institucionales, calendario de eventos y un sistema de admisiones en línea donde los postulantes envían su ficha de inscripción digital.

4.2. Módulo 2: Sistema de Sorteos Unívocos (La Joya de Innovación)

Este módulo resuelve el problema de la desconfianza en las rifas benéficas:

  • Generación Paramétrica de Boletos: El administrador define el nombre del sorteo, precio, fecha límite, número de boletos y genera series alfanuméricas únicas (ej. RM-7489-TX) con códigos QR vinculados.
  • Mesa de Verificación Pública: En la sección pública de sorteos, cualquier persona que adquirió un boleto puede buscarlo por su código.
  • Proceso de Registro Obligatorio y Blindado: Si el boleto está libre, se le pide ingresar:
    1. Nombre completo
    2. Número de teléfono / celular
    3. Correo electrónico
    Al confirmar, el boleto queda automáticamente registrado y vinculado de por vida.
  • Restricción para Usuarios Normales: Por directiva de seguridad y privacidad, un usuario público NO puede borrar boletos, NO puede imprimir boletos masivos y NO puede modificar los datos de otro usuario. Si busca un boleto ya tomado, el sistema únicamente informa con total sobriedad:
    ✅ Boleto Oficial - Registrado por: [Nombre del Participante]
    Protegiendo el número telefónico y correo del participante ante extraños.
  • Modo Bloqueo de Sitio (Sorteo Exclusivo): En el panel de administración existe un interruptor maestro que, al activarse para un evento en vivo, bloquea la navegación general de la web y fuerza a cualquier visitante a ver únicamente la pantalla del sorteo en vivo, ideal para transmisiones de premiación.
  • Ruleta Animada de Ganadores: Algoritmo pseudo-aleatorio basado en crypto.getRandomValues() que simula una ruleta visual de alta fidelidad para elegir al ganador frente a la audiencia.

4.3. Módulo 3: Centro de Operaciones de Ciberseguridad (SOC) & Control de Acceso

Permite al equipo técnico monitorear en tiempo real intentos de accesos no autorizados, registrar direcciones IP, aplicar listas negras instantáneas y, en caso de ataque masivo, activar la Pantalla de Apagón de Emergencia (Emergency Blackout) para resguardar la integridad de los datos.

4.4. Módulo 4: Inventario Inteligente con Escáner QR

Control de activos institucionales (equipos de computación, proyectores, laboratorios) etiquetados con códigos QR. Mediante la cámara del teléfono o laptop (WebRTC API), el administrador escanea el QR en segundos y actualiza el estado y responsable del bien.

6. Banco de Preguntas Trampa del Jurado y Respuestas Maestras

Estudia a detalle estas 10 preguntas. Los jurados universitarios y técnicos suelen hacer preguntas capciosas sobre arquitectura, seguridad, base de datos y escalabilidad.

Arquitectura 1. ¿Por qué eligieron React con Vite en lugar de un framework como Next.js o PHP tradicional en cPanel?
Respuesta recomendada: "Elegimos React con Vite debido a que la aplicación requiere alta interactividad en tiempo real (ruleta de sorteos, buscador instantáneo de boletos, escáner de cámara QR y actualización en vivo mediante WebSockets/listeners de Firebase). Un PHP tradicional requeriría recargas continuas de página (SSR lento) afectando la experiencia de usuario. Además, al compilar con Vite generamos un bundle estático ultra optimizado que se sirve directamente desde la memoria caché de Apache en cPanel con tiempos de respuesta inferiores a 100 ms, eliminando la sobrecarga de procesamiento en el servidor de hosting."
Seguridad 2. Si un usuario malintencionado inspecciona el código en el navegador con F12, ¿puede falsificar un boleto o declararse ganador?
Respuesta recomendada: "Absolutamente no. La validación en el cliente es solo estética. La regla de verdad reside en Firebase Firestore y sus reglas de seguridad (Security Rules). Cuando un usuario registra un boleto, la transacción se ejecuta atómicamente; si el boleto ya posee un `participantName`, la base de datos rechaza cualquier sobreescritura. Asimismo, la ruleta y la elección de ganadores es una función con privilegios de administrador autenticado mediante JSON Web Tokens (JWT), por lo que un usuario sin sesión válida en Firebase Auth recibe un error 403 Forbidden a nivel de protocolo."
Base de Datos 3. ¿Por qué utilizaron una base de datos NoSQL como Firestore en vez de una relacional como MySQL o PostgreSQL?
Respuesta recomendada: "Por tres motivos cruciales: primero, la sincronización en tiempo real sin necesidad de configurar un servidor Socket.io dedicado, lo que permite que cuando un boleto se registre, el panel del administrador lo vea reflejado al instante. Segundo, la escalabilidad elástica: durante un sorteo en vivo el tráfico puede multiplicarse por 100 en minutos; Firestore escala horizontalmente de forma automática sin que el servidor sufra caídas por exceso de conexiones simultáneas. Y tercero, la flexibilidad de esquema documental para manejar estados de boletos y registros de auditoría del SOC."
Protección de Datos 4. ¿Por qué en la consulta pública de boletos solo se muestra el nombre y no el teléfono ni el correo?
Respuesta recomendada: "Por cumplimiento de normativas de protección de datos personales (Habeas Data / GDPR). Si mostráramos el número de celular o correo de quien compró el boleto, cualquier persona que adivine o consulte números correlativos podría recolectar una base de datos privada de números telefónicos para spam o estafas. Al mostrar únicamente `Registrado por: [Nombre]` se brinda certeza y transparencia de que el boleto está ocupado, protegiendo al 100% la privacidad del participante."
Infraestructura 5. ¿Cómo resuelve el archivo .htaccess las rutas en cPanel cuando un usuario recarga la página en `/sorteos` o `/admin`?
Respuesta recomendada: "En las Single Page Applications (SPA), las rutas como `/sorteos` o `/admin` son manejadas en el cliente por React Router y no corresponden a carpetas físicas en el servidor. El archivo `.htaccess` implementa directivas de `mod_rewrite`: comprueba si la petición corresponde a un archivo o carpeta real (`RewriteCond %{REQUEST_FILENAME} !-f`), y si no existe, reescribe silenciosamente la petición hacia `index.html` con código 200. De esta manera, el navegador carga React y el enrutador interno muestra el componente exacto sin arrojar el típico error 404 de Apache."
PWA / Móvil 6. ¿Qué beneficios reales aporta que la aplicación sea una PWA frente a una app nativa de Android/iOS?
Respuesta recomendada: "Elimina la fricción de instalación: el usuario no tiene que gastar memoria descargando 80 MB de una tienda de aplicaciones ni la institución debe pagar membresías anuales a Google Play o Apple Store. Con un solo código fuente mantenemos la versión web, móvil y de escritorio. Además, gracias a los Service Workers, los activos principales quedan en el caché del navegador, lo que permite que el portal abra instantáneamente incluso con señal 3G débil."
Algoritmos 7. ¿Cómo garantizan que la ruleta del sorteo no esté manipulada o trucada?
Respuesta recomendada: "El sorteo utiliza la API criptográfica nativa del navegador `window.crypto.getRandomValues()` en lugar del simple `Math.random()`. `Math.random()` genera números pseudoaleatorios con semillas predecibles, mientras que la API Crypto utiliza fuentes de entropía del sistema operativo, garantizando una distribución estadística uniforme e impredecible entre todos los boletos válidos registrados."
Operaciones 8. ¿Qué sucede si durante la transmisión del sorteo la web sufre un ataque de denegación de servicio (DDoS) o spam masivo?
Respuesta recomendada: "Disponemos de tres capas de defensa: primero, la CDN global de Firebase y las reglas de cuota que absorben picos volumétricos. Segundo, el módulo de Ciberseguridad SOC integrado que permite al administrador identificar y bloquear en tiempo real las direcciones IP agresoras. Y tercero, el botón de 'Bloqueo de Emergencia / Blackout' que desactiva temporalmente peticiones no esenciales y congela el estado para salvaguardar la base de datos."

7. Conclusiones y Recomendaciones

7.1. Conclusiones

  • Se logró con éxito el desarrollo e integración de un portal educativo de alto nivel con un sistema pionero de sorteos criptográficos y un módulo de ciberseguridad SOC en una sola plataforma unificada.
  • La arquitectura sin servidor (Serverless) y el almacenamiento documental en la nube eliminaron la necesidad de servidores locales costosos, reduciendo los costos operativos a prácticamente cero para la institución educativa.
  • El mecanismo de registro unívoco de boletos erradicó el fraude en rifas institucionales, garantizando que una vez registrado un boleto, la autoría quede blindada sin posibilidad de alteración por terceros.
  • El empaquetado para cPanel demostró la viabilidad de desplegar aplicaciones React modernas en hostings comerciales estándar manteniendo soporte para PWA, HTTPS y rutas SPA fluidas.

7.2. Recomendaciones y Trabajo Futuro

  • Integración con pasarelas de pago automatizadas: En una fase posterior, se puede añadir integración con PayPal, Stripe o códigos QR interoperables (PIX/DeUna/Yape) para la compra y pago directo del boleto en la misma plataforma.
  • Notificaciones Push y SMS Masivo: Incorporar el servicio de Firebase Cloud Messaging (FCM) o Twilio para enviar el boleto digital directamente por WhatsApp o SMS al teléfono del comprador al momento de registrarse.
  • Firma Digital de Certificados de Ganador: Generar automáticamente un acta de premiación en PDF firmada criptográficamente con código hash SHA-256 al finalizar el giro de la ruleta.
